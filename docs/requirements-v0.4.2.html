1. What the build must achieve

Workstream leads run their own delivery in their own projects. Everyone involved in the programme, including partners and Gates Foundation contacts, sees one shared programme picture: what is planned, when, how healthy delivery is, what depends on what, and what is waiting for WHO review. Only genuinely sensitive material is kept back, in a small restricted repository. The same issue is never copied to make any of this work.

The two principles the agent must follow:

  • Share operational status and delivery impact; keep sensitive reasoning and internal deliberation private.
  • Issue fields hold the shared values; the projects are different views of them.

2. Design principles

IDPrinciple
DP-01Create once, show many times. One issue can appear in several projects. Never clone an issue to report its status somewhere else.
DP-02Workstream leads own their delivery. The agent creates programme epics and the workstream template. It does not create features or stories in workstream repositories.
DP-03Programme work is not sprint work. Sprints are managed inside the workstream projects. The programme project tracks dates, milestones, delivery health and readiness, not sprints.
DP-04Open by default, restricted by exception. Anything that could affect another workstream's sequencing, dependencies or delivery plans is shared. Only the material listed in section 6 is restricted.
DP-05Technical integration judgements sit with the Technical Integration Lead. The Technical Integration Lead owns technical integration readiness and validation, working with the relevant workstream leads and subject-matter experts. The role is currently held by the WHO WS1 lead, but the authority comes from the role, not from WS1. The PM manages sequencing, dates, dependencies, evidence and escalation, and does not make technical readiness judgements.
DP-06Automation must not make judgements. Automation may make deterministic administrative updates, such as adding items, lifecycle status changes and flags raised from labels. It never makes readiness, approval, risk-acceptance or decision judgements.
DP-07Keep it simple. Delivery health, risk category, impact and dates only. No probability or impact scoring model.
DP-08Prove it small before building it big. A pilot build (section 12) must pass before any bulk import.
DP-09Plain language. All titles, field options, view names and READMEs use plain, simple English. Use the role name "PM & Architecture Integration" exactly as written.

5. Work item taxonomy

5.1 Issue types

Shared organisation rule. The World Health Organization organisation is shared with other WHO teams. Every organisation issue field and every new issue type created for this project is prefixed AAI, for example AAI Workstream or AAI Decision, so it cannot be confused with or collide with another team's. Existing generic issue types (such as Epic, Feature or Task) may be reused if the owners agree. Fields are pinned only to AAI issue types, never to shared generic ones, because pinning shows the field on every team's issues of that type. If the owners do not allow AAI issue types, do not pin; set the fields through the project views instead and record this in the build report. The rest of this document uses the short names without the prefix.

These are created at organisation level (BD-05). If the organisation already has issue types with the same meaning, reuse them.

5.2 Hierarchy

  • Sub-issues represent work breakdown only: Epic, then Feature, then Story or Spike.
  • Research questions are not parents of epics. An item links to research questions through the rq: labels, which list every question it contributes to, including its primary one. The Primary research question field records the main question only, for grouping. The research question issue holds the question, its sub-questions, the rationale and any narrative summary. View V4 is the authoritative list of contributing items; nobody keeps a second list by hand.
  • Milestone issues are not parents of epics either. Items link to Gates outputs through the gates: labels (the complete record) and the Gates output field (the primary output).

5.3 Fields shown on each issue type

Organisation issue fields must be pinned to issue types to appear on the issue form. GitHub allows up to 10 pinned fields per issue type. Pin only these. Fields not pinned to a type can still be set from the project views.

6. Information classification

ClassMeaningWhere it may appear
SharedFine for every partner and Gates Foundation contact to readEverything in aai-programme, the workstream repositories and the programme project
RestrictedNamed WHO staff onlyaai-pm only

Restricted material is limited to:

  • internal deliberations and draft WHO positions not yet agreed
  • escalation notes
  • contractual, funding or personnel matters
  • sensitive security, legal or privacy issues
  • internal review commentary, reviewer details and adjudication reasoning

Rules:

  • SEC-01. Treat everything on an issue in a shared repository as shared: title, body, comments, labels, issue fields and relationships. Anyone with read access to the repository can read its issue fields.
  • SEC-02. Restricted material is never written in a shared repository, including in comments. Put it in an aai-pm issue and link to that issue from the shared one. People without access to aai-pm cannot open the link (pilot test PIL-03 confirms this), but the link text is visible, so it must be neutral, for example "Restricted note". Restricted issue titles must also be neutral, because a title can show in previews.
  • SEC-03. Write shared information on the assumption that every partner and the funder will read it. State facts and the next action, not blame. For example, "Blocked: waiting for the HIV graph schema from WS1, due 20 Nov" rather than an opinion on why.
  • SEC-04. Making any project or repository public is a separate governance decision with its own privacy review. The build must not assume it will happen, and must not prepare for it.
    • Exception: aai-programme is public (owner, 20 October 2026; to be accepted by the PM & Architecture Integration). It therefore holds only material fit for anyone to read, a stricter bar than "shared" in this section. Restricted material stays in aai-pm, linked with neutral text as SEC-02 says.
  • SEC-05. Never weaken repository or project permissions to make linking easier, and never change organisation-wide security settings.

That uses up to 14 organisation issue fields. Before creating any of them, the agent must inspect the organisation's existing issue fields, reuse any compatible fields, and confirm that creating the remainder will not exceed the organisation limit or consume unreasonable shared capacity. If headroom is short, the PM decides which fields to drop; the agent does not choose.

Each project has a limit of 50 fields in total, including system fields and issue fields. Workstream leads can add fields to their own projects, so pre-flight and validation must check both limits.

Notes on meaning:

  • Delivery health describes where the work stands. It is not a WHO judgement of a partner. Risk category and Impact are set only when Delivery health is At risk or Blocked.
  • Next action. When Delivery health is At risk or Blocked, the issue body carries a short "Next action" line: what will happen, who will do it, and by when. It is kept in the body rather than as a field, to save field capacity.
  • Integration readiness is a shared technical delivery status, not an internal WHO assurance judgement.
  • Review status is shared, so partners can see where a review stands. Reviewer details, comments and adjudication reasoning are restricted (section 6).
  • Pipeline stage describes the end-to-end technical flow. Governance and stewardship are cross-cutting; WS5 work uses Cross-cutting / N/A where no pipeline stage applies.
  • Programme status. Programme views use Programme status, not the built-in Status field. The built-in Status is stored separately in each project, so it will differ between projects. Workstream projects keep the built-in Status for their own boards. Do not automatically mirror a workstream project's built-in Status into Programme status.

7.4 Fallback if issue fields are unavailable

If BD-05 or BD-06 cannot be met:

  1. Create the section 7.1 fields as project fields in the programme project, with identical names and options.

9. Dependencies

  • DEP-01. Ordinary technical dependencies use GitHub's native "blocked by" and "blocking" relationships between the issues concerned. Workstream teams create these themselves.

  • DEP-02. A dependency becomes a D-number issue in aai-programme if it is programme-significant: it crosses workstreams or partners and needs a deadline, negotiation, escalation or an assessment of consequences.

  • DEP-03. Each D-number issue links to the waiting epic and to what it waits on. Where that is another epic and the relationship is a true blocking dependency, the agent also creates a native "blocked by" relationship between the two epics. Where the dependency is on a review, an external decision or a shared platform item, no native relationship is created.

  • DEP-04. The agent imports the existing dependency register (D01 to D29) as D-number issues in aai-programme.

  • DEP-05. Do not create extra fields for waiting epic, epic waited on or needed-by date. Each D-number issue uses Workstream (the waiting workstream), Target date (the needed-by date), Delivery health, Risk category, Impact and Assignee. Its issue body follows this template:

    • Waiting workstream
    • Waiting epic
    • Depends on workstream
    • Depends on epic
    • Needed by
    • Consequence if late
    • Next action
    • Owner

11. Automation

IDRequirement
AUTO-01Auto-add to the programme project: aai-programme issues of type Epic, Milestone, Research question, Dependency, Decision or Assumption, and workstream issues (including WS5 items in aai-programme) labelled thin-slice, sprint-demo, blocked or at-risk. AUTO-03A GitHub Action, using the BD-08 credentials. When a programme epic, milestone, research question, dependency or decision issue is created, set Programme status to Not started unless a value was supplied. AUTO-05No automation sets Integration readiness, Review status, Risk category, Impact, a decision or risk acceptance.
AUTO-06Where a saved view or chart can do the job, use it instead of an Action.
AUTO-07Document every automation in the programme project README: what triggers it, what it does, its scope and who owns it.
AUTO-08All scripts are safe to rerun without creating duplicates and have a --dry-run mode. They live in aai-programme/scripts.
AUTO-09If an automation needs a token or raised permissions, stop before creating the secret and report exactly what permission is needed. The BD-08 credentials are expected; any others are not.
AUTO-10Validation check. The Technical Integration Lead confirms validation by adding a comment to the item that starts with Validation confirmed: followed by a short note or evidence link. A scheduled Action checks every item whose Integration readiness is Validated. If there is no confirmation comment from the Technical Integration Lead, it adds the validation-exception label and one comment explaining why. It is idempotent: it never adds a second comment for the same exception. When the confirmation comment appears, or the value moves off Validated, it removes the label. It never changes Integration readiness. The Technical Integration Lead's GitHub username is a setting in aai-programme/scripts, not hard-coded.
AUTO-11Backfill. Auto-add workflows only catch items created or updated after they are switched on. A one-off script, run in build step 8, adds existing qualifying items to the programme project.
AUTO-12Optional. A weekly script calculates M6 (average age of blocked items) from the issue timelines and posts it as a comment on a pinned "Programme metrics" issue in aai-programme. Not part of the pilot. Build it only after the pilot passes, and only if there is capacity; M1 to M5 are enough to start with.

Integration readiness is proposed by the relevant workstream lead, who sets Ready to integrate. The Technical Integration Lead then posts the Validation confirmed: comment with the supporting evidence and sets Validated (DP-05). Automation never sets Validated. The confirmation comment is the authoritative validation record because it captures an explicit approval and lets the Technical Integration Lead point to the evidence. GitHub records issue field changes in the issue timeline, and that history may be used as additional audit information, but changing the field alone does not count as validation. Validation is never inferred from closed sub-issues.
