3. Decisions needed before the build

The agent may carry out step 1 of section 13 (pre-flight) at any time. It must not configure or create anything from step 2 onward until every decision relevant to that step is confirmed. Each decision has a recommended default.

IDDecisionRecommended defaultWhy it matters
BD-01GitHub organisationDecided: the existing World Health Organization organisation, shared with other WHO teams. Login: WorldHealthOrganization (https://github.com/WorldHealthOrganization)Everything sits in it. Because the organisation is shared, the safeguards in BD-01a apply
BD-01aShared organisation safeguards: (1) the current base permission for members. If it is anything other than "No permission", partners invited as members could read other WHO teams' repositories, and the build must not change it (SEC-05); (2) how many of the 25 organisation issue fields are already used by other teams; (3) which issue types already exist; (4) whether the owners will allow project-specific issue types, and pinning fields to them; (5) that the agent works through a named account with delegated rights, never a shared loginWHO GitHub owner to confirm before step 2. If (1) cannot be met, partners join as outside collaborators instead (see BD-03)Organisation-wide settings, issue fields and issue types affect every WHO team using the organisation, not just this project
BD-02All Assured AI coordination repositories (programme, restricted and workstream repositories holding issues, features, stories and spikes) sit in that organisationDecided: yesIssue fields only work on issues in repositories owned by the same organisation
BD-02aPartner source-code repositories, models and other technical assets may stay in partners' own GitHub organisationsDecided: yes, where partners need itTheir work is still tracked through issues in the WHO workstream repositories, which link to the external repository. Issues held in external repositories are never added to the programme project
BD-02bHow each workstream will link external technical assets, if any, to its WHO-hosted coordination issuesWorkstream lead to confirm before bulk importEach workstream needs a consistent way to point from a WHO issue to the partner's code, for example a link in the issue body or a pull request reference
BD-03Partners join as organisation membersDecided: members, subject to BD-01a(1) and the checks in BD-03a. If the base permission cannot be "No permission", fall back to outside collaborators with access granted per repository. Whichever model is used for partners and for Gates Foundation contacts is recorded in the build report and the programme READMEOnly organisation members can belong to GitHub teams. Recording the model matters when new partners or contacts are added later
BD-03aChecks before partners are invited: (1) whether the organisation uses SAML single sign-on or Enterprise Managed Users, and if so how partners get WHO identities; (2) seat cost per partner member; (3) base permission for members set to "No permission"; (4) members cannot create repositories or change visibilityWHO GitHub owner and WHO IT to confirmWith single sign-on, members must sign in through WHO's identity provider. With Enterprise Managed Users, WHO's identity system must create the accounts. Either could block or delay partner access
BD-03bA test account with partner-level access for the pilotWHO GitHub owner to provide one test account, removed after the buildPilot tests PIL-03 and PIL-07 need a real user with partner access. The agent cannot create GitHub accounts
BD-04Repository rolesPartners: Read on aai-programme; Maintain for the workstream lead and Write for the team on their own workstream repository; Triage on other workstream repositories where they contribute. Gates Foundation contacts: Read on aai-programme and the workstream repositories, and read access to the programme project. Nobody outside named WHO staff has access to aai-pmTriage lets people manage issues without changing code
BD-05Organisation owners willing to create issue fields and issue typesOne named WHO owner to run step 2 of section 13Only organisation owners can create issue fields and issue types
BD-05aInspect the organisation's existing issue fields before creating any new onesReuse compatible existing fields; do not duplicate themThe organisation-level field limit is shared across the whole organisation
BD-06Issue fields available on WHO's GitHub plan and permitted by WHO enterprise policyCheck and confirmIf they are unavailable or restricted, the fallback in section 7.4 applies
BD-07Gates Foundation contacts have access to the programme projectDecided: yes. They see everything that is shared, including delivery health and review statusShared information must be written on the assumption that the funder will read it (SEC-03)
BD-08Credentials for the GitHub Actions in section 11Prefer a GitHub App with least-privilege permissions where WHO policy supports it; otherwise an approved fine-grained token. A WHO GitHub owner creates it and stores it as an organisation secret available only to the repository that holds the scriptsAUTO-03, AUTO-04 and AUTO-10 write to issue fields across repositories, which the default Actions token cannot do. The agent must not design, create or embed credentials itself
